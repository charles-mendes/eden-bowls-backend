# Proposal

## Why

QA and local development still share one Stripe sandbox (the Charles test account) for both countries, and that same account is what the QA API verifies webhooks with. Billing now has a separate QA pair and a separate live pair, each with its own Brazil account and its own United States account. Charges, customers, and webhook signatures from one environment must not land on another environment's merchant account. Object ids saved from the Charles account do not exist on the new accounts.

## What Changes

- Retire the shared Charles sandbox from the QA host and from local development. QA and localhost use the QA Brazil sandbox and the QA United States test account. "Área Restrita" is Stripe's Portuguese name for a sandbox. It is not a restricted key (`rk_`). Production uses the live Brazil account and the live United States account.
- Keep the existing variable names and the existing paths `POST /stripe/v1/webhook/br` and `POST /stripe/v1/webhook/us`. Each host's `.env` holds only that host's secret keys and that host's webhook signing secrets. Live keys never go on QA or on a developer machine.
- Rotate the live secret keys and the live webhook signing secrets, and the QA secret keys and QA webhook signing secrets, before any host is configured. The values pasted into the planning chat are compromised. Publishable keys stay; they are public.
- Point the Stripe dashboards at the API, not the store. Each of the four endpoints subscribes to the 28 events in `src/infrastructure/stripe/stripe-webhook-events.js` and uses API version `2025-09-30.clover`:
  - QA Brazil: `https://qa-api.edenbowls.com/stripe/v1/webhook/br`
  - QA United States: `https://qa-api.edenbowls.com/stripe/v1/webhook/us`
  - Production Brazil: `https://api.edenbowls.com/stripe/v1/webhook/br`
  - Production United States: `https://api.edenbowls.com/stripe/v1/webhook/us`
- `api.edenbowls.com` is not in this repo's Caddyfile. DNS, TLS, and a reverse proxy to the production API are an external prerequisite. The production webhook test does not start until that host routes the two paths to the API.
- Do not map Charles `cus_`, `sub_`, `price_`, `prod_`, or `coupon_` ids onto the new accounts. On QA, stop the store, write secrets, dump the Stripe tables, then delete ledger rows created before a cutoff. `stripe_account` is only `br` or `us`, so the delete is by `created_at`, not by merchant account. The script runs only when `EDEN_RUNTIME` is `qa` or `local`, with `--confirm-delete-ledger` and `--created-before`. A second run is refused by a row in the existing `background_job_cursors` table, not by a file in the container. Then sync the catalog and coupons once. Developer databases copy those ids by parent slug plus flavor and weight, including product meta, and do not run catalog sync. There is no schema migration. The Charles sandbox is disconnected: its webhook endpoint aimed at `qa-api` is removed, its pasted secret is rolled, and its test subscriptions are canceled or the sandbox is removed.
- Keep the account choice on the shipping-address country, not on the site domain. `BR` uses the Brazil secret and `VITE_STRIPE_PUBLISHABLE_KEY_BR`. `US` uses the United States secret and `VITE_STRIPE_PUBLISHABLE_KEY_US`. Brazil is charged in BRL and the United States in USD. A missing Brazil catalog currency MUST NOT fall through to USD. Checkout uses `_stripe_price_ids_by_currency` for that currency and does not fall back to the single `_stripe_price_id`. The store aborts when the API returns a `stripe_account` that does not match that country. `parseEnv` refuses to boot unless `EDEN_RUNTIME` is `local`, `qa`, or `production`. Checkout stamps `metadata.eden_env` from that value on customer create, subscription create, plan-edit metadata, and the PaymentIntent, and the client secret is returned only after that PaymentIntent update. `invoice.paid` and subscription changes apply only when the marker matches. A missing or different marker returns 200, writes nothing, and logs a warning. An unset `EDEN_RUNTIME` is not treated as a match for a missing marker.
- Local webhook signing secrets stay the per-machine values printed by `stripe listen` against the QA accounts. They are not the QA dashboard signing secrets and they are not the live signing secrets.
- The store build for an environment uses the publishable key of the same merchant account as that environment's API secret (`VITE_STRIPE_PUBLISHABLE_KEY_BR` and `VITE_STRIPE_PUBLISHABLE_KEY_US`). QA and local use the QA test publishable keys. Production uses the live publishable keys. Changing them requires a store rebuild. This backend change does not edit the store repo.
- Secret keys, publishable keys, and webhook signing secrets stay out of git, docs, examples, and this change. `.env.example` and `.env.qa.example` keep the names and empty values.
- QA and production hosts that take Brazil checkout set `STRIPE_BR_ENABLED=true` only after that host has its Brazil secret, its Brazil webhook secret, and a Brazil catalog on that account. The empty template default stays `false`.
- `EDEN_RUNTIME` is written on the QA host, on developer machines, and on a production API host if one is already running, before the boot guard is merged. QA deploy runs automatically after CI succeeds on `main` and rebuilds `api` and `cron` from the host `.env`. Both services use `env_file: .env`. The running code does not read `EDEN_RUNTIME`. The guard is merged in the cutover window, because Charles subscriptions have no marker and are then ignored.
- The two live webhook endpoints stay disabled until `api.edenbowls.com` routes both paths and the live signing secrets are already in the restarted API. Production writes secrets only after `stripe_subscriptions` and the three customer meta keys each count as zero. A ledger row whose price id is a seed placeholder is not accepted. Then stop the store, write secrets, restart, enable the endpoints, sync the catalog, and open. QA rollback restores the previous `.env` together with the dump taken before the retire script. Production rollback stops the store and sets `STRIPE_BR_ENABLED=false`. That flag does not stop United States checkout.

## Capabilities

### New Capabilities

- None.

### Modified Capabilities

- `stripe-region-config`: Each environment binds its own Brazil and United States merchant accounts. QA and local development use the QA test accounts. Production uses the live accounts. Stored Stripe ids from the retired sandbox are recreated or retired locally. Checkout, the publishable key, the webhook secret, and the currency stay on the address country. Webhook endpoints subscribe to the shared event list at the pinned API version. Compromised secrets are rotated before a host is configured.
- `production-readiness`: The go-live checklist records the operator-supplied webhook URLs, states that `api.edenbowls.com` must be provisioned outside this repo before a live webhook test, keeps the live endpoints disabled until then, and states that production Stripe rollback stops the store because `STRIPE_BR_ENABLED` only covers Brazil.

## Impact

- No new HTTP route and no change to how `parseEnv` reads `STRIPE_US_*` and `STRIPE_BR_*`. `parseEnv` gains a required `EDEN_RUNTIME` of `local`, `qa`, or `production`, with no default. `NODE_ENV=production` is already set on QA, so it cannot tell a QA test key from a live key. QA `api` and `cron` both load that variable from `env_file: .env`. Neither `environment:` list sets it. Local `docker-compose.backend.yml` does the same for its only `api` service. No schema migration. `background_job_cursors` already exists and holds the retire marker.
- Catalog and billing rows are account-scoped. Checkout reads `_stripe_price_id` and `_stripe_price_ids_by_currency` from post meta. The ledger stores `stripe_customer_id`, `stripe_subscription_id`, and `stripe_price_id` with `stripe_account`. Customer meta stores `_hsr_stripe_customer_id_br` and `_hsr_stripe_customer_id_us`. The US read still falls back to `_hsr_stripe_customer_id`. `stripe_first_purchase_promos` stores `coupon_id` and `promotion_code_id` per `stripe_account`. The seed writes `prod_seed_*` and `price_seed_*`, which are not real Stripe ids.
- Account selection already exists. The API uses `resolveStripeAccountFromCountry` (`BR` or `US` only). The store uses `stripeAccountFromCountry` on the same address and checks `stripe_account` on the checkout response. `POST /stripe/v1/webhook/br` verifies with the Brazil signing secret and `POST /stripe/v1/webhook/us` with the United States secret. A missing catalog currency on a Brazil checkout currently falls through to `usd` in `onboarding-subscription-checkout.service.js`. That fallback goes away for Brazil. `lookupStripePrices` currently falls back to `_stripe_price_id` when the currency map has no entry. That checkout fallback goes away. `hasStrictStripeBinding` in `products.repository.js` already requires the currency map and still reads the single field as a presence check. Admin catalog still writes both fields. `runLedgerReconcile` reads every ledger row through `listAfterId`, which has no status filter, and a retrieve error increments `failed` without logging the error or stopping the job. `resolveUserContext` can attach a webhook to a user from `metadata.wp_user_id`. `EDEN_RUNTIME` does not exist yet. `stripe listen` forwards the whole event list, including QA checkouts, to the laptop. The only `subscriptions.create` is `createOnboardingSubscription`. Plan edit sends metadata from `subscriptions-edit-commit.repository.js`. Pause, resume, and payment-method updates do not send metadata.
- Operator config outside git: rotated secrets on the QA API host, the production API host, and local `.env` files, plus the matching store publishable keys and a store rebuild.
- Docs: `docs-new/FEATURE_STRIPE_SEPARAR_PAISES/COMO-CONFIGURAR-STRIPE.md`, `docs-new/BUG_CHECKOUT_BACK_AND_FRONT_END/STRIPE_CLI_WEBHOOK_LOCAL.md`, and `docs/production-go-live.md`.
- Deploy workflows keep reading the host `.env`. They do not gain Stripe secrets as GitHub Actions secrets. `.github/workflows/deploy.yml` publishes QA after a successful CI run on `main`. There is no production deploy workflow. `bootstrap` calls `parseEnv` before migrations, so a missing label fails the new container before SQL runs.
- Assumption: localhost has no fifth Stripe account. It uses the QA test accounts, with CLI forwarding, and shares those test accounts with the QA server. Live keys are not used locally.
